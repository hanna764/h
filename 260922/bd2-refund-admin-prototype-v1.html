1. 왜 어드민이 본체인가

유저 화면은 결제창 하나다. 어려운 것은 전부 뒤에 있다. 상품마다 쿠폰과 마일리지가 다르게 붙어 있고, 통화가 80종이 넘고, 결제수단마다 부분환불 가부가 갈린다. 운영자가 이 조합을 손으로 계산하면 반드시 틀린다.

설계 원칙 — 운영자의 입력은 "어느 상품을 환불할지" 하나뿐이다. 금액, 복구할 쿠폰, 복구할 마일리지, 가능한 처리 경로는 전부 시스템이 산출해 화면에 띄운다. 운영자는 읽고 버튼을 누른다.

2. 통화 80종을 어떻게 다루나

환율 변환이 필요 없다. 재결제는 원 주문과 같은 통화, 같은 금액 체계로 청구하기 때문이다. 시스템은 주문 확정 기록(정책 50번)에 박아둔 상품별 실결제액을 그대로 더할 뿐이다.

  • 정수 표기 20개국은 버림, 소수점 표기국은 2자리 내림 — 정책 23번을 그대로 따른다
  • 재결제 금액이 해당 통화의 최소 결제 금액에 미달하면 개인결제 경로를 막고 전체환불로 유도한다(정책 19·24번)
  • 환율이 개입하는 곳은 CS 계좌 입금 하나뿐이다. 국가 변경 유저 케이스이며 정책 69번에서 별도로 다룬다

3. 쿠폰과 마일리지가 진짜 어려운 부분

원 결제를 전체취소하면 그 결제에 쓰인 쿠폰 전량과 마일리지 전액이 되살아난다. 그런데 유지하는 상품에도 쿠폰과 마일리지가 붙어 있었다. 그래서 재결제에 그것들을 다시 소모 처리해야 유저 부담이 원래와 같아지고, 쿠폰이 이중으로 되살아나지 않는다.

예시 — 원 결제 101,900원

A 코스튬(20% 쿠폰 적용, 39,200) 유지 · B 다이아(10% 쿠폰 + 마일리지 2,000, 27,700) 환불 · C 성장팩(마일리지 4,000, 35,000) 환불
→ 전체취소로 쿠폰 2장과 마일리지 6,000이 복구됨
→ 재결제 39,200원에 20% 쿠폰 1장을 다시 소모 처리
→ 유저에게 최종 남는 것: 쿠폰 1장(10%)과 마일리지 6,000

이 계산을 운영자가 하면 안 된다. 어드민이 "복구 후 재소모될 쿠폰"과 "복구될 마일리지"를 명시해 보여주고, 실행 버튼 한 번에 전부 처리해야 한다.

4. 가장 위험한 지점 — 2단계 트랜잭션

개인결제건 발급→ 유저 재결제 성공→ 원 주문 전체취소→ 완료
재결제는 성공했는데 원 주문 취소가 실패하면

유저는 101,900원과 39,200원을 동시에 부담한 상태로 남는다. PG 장애, 결제수단 취소 기한 초과, 네트워크 유실 어느 것으로도 발생할 수 있다. 이 상태를 감지하지 못하면 유저가 항의할 때까지 아무도 모른다.

  • 자동 재시도 3회. 실패하면 상태를 취소실패(긴급)로 두고 대시보드 최상단에 고정한다
  • 유저 화면에는 실패를 단정하지 않는다. "환불 처리 중"으로 표시한다(화면 상태 11번과 같은 원칙)
  • 최후 수단은 역방향 롤백이다. 개인결제건 자체를 환불하고 원 상태로 되돌린다
  • 순서를 바꾸면 안 된다. 먼저 전체취소하고 나중에 재결제받는 구조는, 유저가 재결제를 하지 않으면 이미 소진한 상품까지 무상으로 가져가게 된다. 회수 수단이 없다

5. 경로 판정을 시스템이 한다

운영자가 "이 건은 무슨 경로로 처리해야 하지"를 판단하지 않게 한다. 결제수단과 지급 상태만 보면 기계적으로 정해진다.

조건경로

원래 금액 · 쿠폰 할인 · 포인트 사용이 결제 단위로 한 세트뿐이다. 결제 1건에 상품 1개라는 전제로 만들어졌기 때문이다. 장바구니가 들어오면 이 세 값이 상품 수만큼 반복되어야 하고, 그 순간 이 화면은 통째로 다시 만들어야 한다.

3. 현행 환불 모달의 실제 동작

요청 본문은 { transactionId, reason } 두 개뿐이다. 금액 파라미터가 없다. 부분환불을 표현할 방법이 구조적으로 없다는 뜻이다.

모달에 노란 경고 박스로 이렇게 적혀 있다. "환불 처리 시 다음 작업이 수행됩니다."

  • 사용된 쿠폰 복구
  • 사용된 포인트 환불
  • 적립된 대기 포인트 삭제
  • 결제 상태를 REFUNDED로 변경

확인 문구는 "정말 환불하시겠습니까? 이 작업은 취소할 수 없습니다."이며 환불 사유는 필수 입력이다. 결제 상태 enum은 COMPLETED · FAILED · REFUNDED · PENDING · CANCELED다.

확인된 것 — 정책 정의서와 일치

정책 12번(마일리지 사용분 복구, 적립예정분 취소)은 이미 구현되어 있다. 정책 6번(쿠폰 복구)도 현행은 무조건 복구다. 즉 "환불 시 쿠폰을 복구하지 않는다"로 바꾸려면 기존 동작을 끄는 개발이 필요하다. 없던 것을 만드는 게 아니다.

4. 포인트(마일리지) 관리 화면은 이미 상당히 완성되어 있다

현황(현재 포인트 · 예정 만료된 포인트), 포인트 지급 · 차감, 대기 포인트 지급 · 차감이 모두 있다. 금액 입력은 "소수점 가능"이라 통화별 자릿수에 이미 대응한다. 기능별 권한 체크도 걸려 있다.

그래서 마일리지 환급은 신규 개발 없이 오늘도 수동 처리가 가능하다. 9/21 회의에서 마일리지를 운영 수동 대응으로 두고 재결제를 1차 개발로 올린 판단이 실측으로 뒷받침된다.

5. 없는 것 — 신규 개발 대상

없는 것영향
주문(order) 개념 자체/api/orders가 존재하지 않는다. 결제(payments)만 있다. 주문 1건에 상품 N행 구조는 API 신설이다
부분환불금액 파라미터가 없어 표현 불가
개인결제창관련 엔드포인트 전무. 완전 신규
지급 상태 정보우편함 대기 · 인벤 보관 · 소진 구분이 어드민에 없다. 정책 59번 판정을 화면에서 할 수 없다
환불 접수 큐조회 후 바로 환불. 접수 · 검토 · 실행의 워크플로가 없다
환불 사유 코드자유 텍스트 1칸. 정책 17번의 사유 3종 구분이 불가

엔드포인트용도

운영자가 체크박스를 누를 때마다 서버가 계산해 돌려준다. 브라우저에서 계산하면 화면과 실제 처리 금액이 어긋날 수 있다. 정책 53번(서버 재계산, 브라우저가 보낸 금액은 신뢰하지 않음)의 어드민판이다. execute 는 simulate 가 돌려준 산출 해시를 같이 받아, 그 사이 값이 바뀌었으면 거부한다.

3. 기존 API 변경

대상변경
POST /api/payments/refund금액과 대상 lineId 목록을 받도록 확장하거나, 부분환불 전용 엔드포인트를 신설하고 기존은 전체환불로 남긴다. 후자를 권고 — 기존 호출부의 동작이 조용히 바뀌지 않는다
환불 시 쿠폰 복구현행은 무조건 복구. 정책 6번 확정에 따라 켜고 끌 수 있어야 한다 (정책팀 회신 10/02)
환불 사유자유 텍스트 → 사유 코드 3종(유저 요청 · 회사 귀책 · 차지백) + 메모. 정책 17번
결제 상세 화면상품별 반복 구조로 전면 개편. 현행 단일 세트 표시로는 장바구니 주문을 읽을 수 없다

4. 개인결제 상태 전이

발급→ 결제대기→ 취소처리중→ 완료
발급→만료 취소처리중→취소실패→수동 처리 또는 롤백
  • 유효기간은 결제수단의 취소 가능 기한보다 짧게 잡는다. 기한을 넘기면 원 주문 취소 자체가 불가해져 취소실패가 확정된다
  • 발급 시점에 유지 lineId 목록과 청구금액을 고정한다. 그 사이 원 주문이 다른 경로로 환불되면 발급건을 자동 무효화한다
  • 같은 주문에 개인결제건이 둘 이상 살아 있을 수 없다. 발급 시 기존 건을 취소한다

5. 권한

현행 어드민에 이미 권한 체계가 있다(/api/permissions, /api/permissions/menus). 포인트 지급·차감에 권한 체크가 걸려 있는 것을 번들에서 확인했다. 신규 기능도 같은 체계에 얹는다.

동작권한 수준
환불 접수 생성 · 산출 조회운영 일반
PG 부분환불 실행운영 일반
마일리지 환급 실행운영 일반 (현행 포인트 지급 권한 준용)
개인결제건 발급운영 일반
취소실패 건 수동 처리 · 롤백상급 — 유저 이중 부담 상태를 건드린다
CS 계좌 입금상급 + 건별 지출결의

6. 개발팀에 물어야 할 것

  • 개인결제창을 엑솔라로 어떻게 여는가 — 합산 금액 방식이면 임의 금액 토큰 발급이므로 기술적으로는 기존과 같다. 다만 그 토큰을 특정 유저에게만 유효하게 묶는 방법이 필요하다
  • 원 주문 전체취소의 실패율과 실패 사유 — 현행 /api/payments/refund 운영 실적에서 뽑을 수 있다. 이 숫자가 취소실패 대응의 설계 강도를 정한다
  • 결제수단별 취소 가능 기한 — 개인결제 유효기간의 상한이 된다
  • 지급 상태를 어디서 가져오는가 — 우편함 · 인벤 · 소진 구분은 게임 서버 정보다. 어드민이 실시간 조회할지, 주문에 동기화해 둘지
  • simulate 산출을 서버에서 할 때 게임 서버 왕복이 필요한가 — 필요하다면 응답 지연이 운영 체감을 좌우한다
